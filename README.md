# Crusoe Cloud Go Client

This repository hosts the official Crusoe Cloud golang API client. The client is entirely autogenerated from our API's OpenAPI spec.

## Authentication

Two credential types are supported: a static access key/secret key pair, and OAuth2 service-account client credentials.

```go
// Static key.
client := auth.NewAuthenticatedAPIClient(accessKey, secretKey)

// Service account.
client, err := auth.NewClientSecretAPIClient(ctx, clientID, clientSecret, tokenURL, audience)
```

To auto-detect which credential type to use, resolved in this order - explicit options, then
environment variables, then `~/.crusoe/config` - use `NewDefaultAPIClient` instead:

```go
client, err := auth.NewDefaultAPIClient(ctx)
```

### Config file

`~/.crusoe/config` is TOML, with one table per named profile. A top-level `profile` key selects
the default profile when none is specified another way:

```toml
profile = "default"

[default]
access_key_id = "..."
secret_key = "..."

[my-service-account]
client_id = "..."
client_secret = "..."
# token_url and audience are optional, defaulting to the production endpoint.
```

A table may hold either an access key pair (`access_key_id` / `secret_key`) or a service account
pair (`client_id` / `client_secret`, optionally `token_url` / `audience`) - not both.

`auth.WithProfile(name)` selects a named profile from the config file. A profile selected this
way takes precedence over environment variables, not just the config file's own default profile -
so one process can hold multiple identities (e.g. different service accounts for different
projects) without unrelated `CRUSOE_*` environment variables overriding which one gets used. If
the named profile is missing or incomplete, resolution fails rather than falling through to env
vars that may belong to a different identity. `WithProfile` cannot be combined with `WithAPIKey`
or `WithClientSecret` - both select an identity, so combining them is rejected as ambiguous rather
than silently picking one.

Environment variables: `CRUSOE_ACCESS_KEY_ID` / `CRUSOE_SECRET_KEY` for a static key,
`CRUSOE_CLIENT_ID` / `CRUSOE_CLIENT_SECRET` (optionally with `CRUSOE_TOKEN_URL` /
`CRUSOE_AUDIENCE`) for a service account.
Configuring both at once is an error.

`auth.WithConfigPath(path)` (or the `CRUSOE_CONFIG_DIR` environment variable) points at a config
file in a non-default location, for processes with no home directory or that keep their config
file elsewhere.

## Project tooling

Run `mise install`, then use the existing Make targets or `mise run` directly.
Tool versions and local workflow ordering live in root `mise.toml`; `mise.lock`
resolves macOS arm64 and Linux amd64 (including musl).

CI uses the shared mise/Go components from tools `master`: count coverage and
race checks run separately, lint runs on MR pipelines, and release tagging follows
the shared dependency policy. Central security policy scans
remain enabled. Local `make test-ci` uses the shared count coverage reports
(`coverage.out`, `coverage.html`, `coverage.xml`, and `junit.xml`) and runs race
checks separately; `make ci` also runs local lint. Coverage excludes generated
protobuf files and mocks/proto packages, and Cobertura reports coverage by file.
`BUILDTAGS` and native `GOFLAGS` remain supported for test selection.

This migration upgrades the project tooling to Go 1.26.10 and golangci-lint v2.
The v2 lint configuration maps maintained checks and retains the generated
Swagger exclusion; removed upstream checks are listed in the migration review.

The v1-only `ifshort` and `exportloopref` checks remain available through
`mise run lint:legacy-checks` and MR CI on their compatible Go 1.18 lint runtime.
The module language version remains Go 1.17. `make lint` and local CI/development
workflows include those checks, v2 lint, and the separate v2 formatting check.
